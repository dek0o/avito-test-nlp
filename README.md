# Avito: кандидатогенерация для поиска услуг

Решение тестового задания Авито по кандидатогенерации в поиске услуг. Пользователи ищут услуги короткими запросами ("автоподбор", "монтаж видеодомофонов"), и для каждого запроса нужно отобрать из корпуса (189k объявлений) до 50 кандидатов, которые дальше уйдут на ранжирование. Подходящими считаются объявления, которые пользователь в итоге выбрал по этому запросу.

Метрика: Recall@50, то есть доля подходящих объявлений, попавших в топ-50, усреднённая по запросам. Порядок внутри топ-50 не важен.

Данные: `train.parquet` (498k пар "запрос - выбранное объявление"), `benchmark_queries.parquet` (2452 запроса без разметки) и `benchmark_items.parquet` (корпус объявлений для поиска).

## Результат

- Бейзлайн (BM25, приоры локации и подкатегории, фильтры): локальная валидация 0.910, лидерборд 0.8476.
- Двухэтапная модель (пул из 500 кандидатов по бейзлайну и эмбеддингам USER2, затем LightGBM LambdaRank): локальная валидация 0.951, лидерборд 0.9066.

Локальная валидация здесь означает 5-fold CV на 11k запросах чистой валидации (см. ниже).

## Подход

Подробный разбор с выводами находится в [solution.ipynb](solution.ipynb).

1. EDA. Бенчмарк состоит из уникальных хвостовых запросов: только 37% текстов встречались в train. Корпус почти не пересекается с train по объявлениям. Главные сигналы:
   - локация: в 95% случаев объявление находится в пределах 22 км, 17% поисков заданы по региону;
   - подкатегория: запрос на 86% определяет её;
   - фильтры запроса: совпадают с параметрами объявления в 94-98% случаев;
   - текст описания: без него все слова запроса находятся только в 62% пар.
2. Бейзлайн. Многополевой BM25 (веса полей: заголовок 3, параметры 1, описание 2; стемминг Snowball), лог-приор `p(локация объявления | локация поиска)`, лог-приор `p(подкатегория | запрос)` через kNN по похожим запросам train и штраф за несовпадение фильтров.
3. Этап 1 финальной модели. Пул из 500 кандидатов по скору бейзлайна плюс косинус эмбеддингов [`deepvk/USER2-base`](https://huggingface.co/deepvk/USER2-base). Полнота пула 0.987.
4. Этап 2. LightGBM LambdaRank на 38 признаках: текстовые (BM25 по полям, покрытие слов, символьное сходство), географические (расстояние, конкуренция в локации), подкатегория, фильтры, свойства объявления, косинус эмбеддингов.

Про валидацию. Если добавлять позитивы отложенных сессий в корпус, появляется артефакт: такие объявления отличимы от родных объявлений корпуса (AUC 0.69), и ранкер учится их узнавать. Поэтому ранкер обучается и оценивается только на сессиях, где выбранные объявления есть в `benchmark_items`. Подробности в разделе 3.1 ноутбука.

## Запуск

```bash
pip install -r requirements.txt
```

1. Данные предоставляются вместе с заданием и в репозиторий не входят. Положить три файла в папку `data/` в корне репозитория:
   ```
   data/train.parquet
   data/benchmark_queries.parquet
   data/benchmark_items.parquet
   ```
2. Выполнить `solution.ipynb` целиком. Результат будет в `answer.csv` (финальная модель) и `answer_baseline.csv`.

Время: около 25 минут на Apple M4 / 16 ГБ RAM. Эмбеддинги корпуса и запросов уже лежат в [artifacts/](artifacts/) (USER2-base, первые 128 координат по Matryoshka) и загружаются оттуда. Если удалить `artifacts/`, они пересчитаются: модель скачается с HuggingFace (около 570 МБ), кодирование корпуса займёт около 1.5 часа на MPS. Устройство выбирается автоматически (CUDA, затем MPS, затем CPU). На CPU кодирование корпуса заметно дольше.

Проверено на Python 3.12, macOS, Apple M4.

## Входные данные

Ожидаются три файла Parquet в папке `data/`. В начале ноутбука `check_inputs` (`src/data.py`) проверяет их и падает с понятным сообщением, если чего-то не хватает.

`train.parquet`: одна строка на пару "запрос - выбранное объявление". Нужные колонки:
- признаки запроса: `search_query` (строка), `search_location_id` (int), `search_infm_params_text` (строка, может быть пустой), `search_category` (int), `search_is_delivery_search` (0/1, используется только в EDA);
- признаки объявления: те же колонки, что в `benchmark_items.parquet`.

`benchmark_queries.parquet`: `query_id` (уникальная строка) и те же пять признаков запроса.

`benchmark_items.parquet`: `item_id` (уникальная строка), `item_title_raw`, `item_description_raw`, `item_infm_params_text` (строки), `item_category_id`, `item_microcat_id`, `item_location_id` (int), `item_price`, `item_latitude`, `item_longitude` (числа, допускаются строки и Decimal), `item_rating`, `item_rating_reviews_count` (float, допускаются пропуски), `item_is_phone_hidden`, `item_is_message_forbidden` (bool).

Другие колонки игнорируются, порядок строк не важен.

Неявные требования к содержимому:
- фильтры запроса разбираются по ключам "Вид услуги", "Тип услуги" и "Тип услуги автосервиса", а в параметрах объявления ищутся те же фразы. При другом формате фильтры просто перестанут учитываться, остальное будет работать;
- часть объявлений, выбранных в train, должна быть в корпусе. На таких сессиях обучается ранкер и строится чистая валидация, нужно хотя бы 1000 уникальных запросов. Сейчас их около 11k, это 6.6% строк train. Если пересечения нет, `split_in_corpus` остановится с объяснением.

## Если входные данные изменятся

Все статистики, индексы и модели пересчитываются по новым данным при прогоне ноутбука, ничего не зашито под текущие файлы. Отличаются по стоимости только эмбеддинги:
- эмбеддинги в `artifacts/` сопоставляются по `item_id` и тексту запроса. Кодируются только новые объявления и запросы, а файлы в `artifacts/` перезаписываются под текущие данные. Для этого нужна модель: при первом запуске она скачается с HuggingFace;
- новый бенчмарк с тем же корпусом: докодируются только запросы, это секунды;
- новый train: меняется разбиение для ранкера, докодируются его запросы, около минуты;
- новый корпус: кодируются только новые объявления, около 1.5 часа на каждые ~190k объявлений на Apple M4.

Выводы и цифры в markdown-ячейках ноутбука описывают текущие данные. При новых данных их нужно сверить с выводами ячеек.

Ограничения по ресурсам: при текущих размерах пиковое потребление памяти ядром около 9 ГБ (замерено), так что нужна машина с 16 ГБ RAM. Память растёт примерно линейно с числом запросов в чистой валидации и с размером корпуса.

## Структура

```
solution.ipynb      EDA, бейзлайн и финальная модель с выводами
src/common.py       нормализация и токенизация, многополевой BM25, разбор фильтров, метрика
src/data.py         загрузка и разбиения train, в том числе чистая валидация split_in_corpus
src/baseline.py     бейзлайн-ретривер: BM25, приоры локации и подкатегории, фильтры; этап 1
src/dense.py        эмбеддинги USER2-base (Matryoshka 128), кеш в artifacts/
src/features.py     признаки пар "запрос - кандидат" для ранкера
src/ranker.py       LightGBM LambdaRank, отбор топ-50
artifacts/          готовые эмбеддинги корпуса и запросов
answer.csv          ответ финальной модели
```

## Open-source компоненты

numpy, pandas, scipy, scikit-learn, PyStemmer (Snowball), LightGBM, sentence-transformers, модель `deepvk/USER2-base` (Apache 2.0). Всё работает локально, без внешних API.
